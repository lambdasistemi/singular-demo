**How the sink decides.** The sink does not trust what the transaction tells it. The transaction hands it a pointer to an output (the redeemer), and the sink reads that output itself: it must hold exactly one token of the name under the registry's active policy, and its datum must be the key's record, with the payload an address. A pointer to any other output is refused, and so is a transaction that does not carry the pointed output as a reference input. Then it counts: everything that leaves the sink, every kind of asset, must arrive at that address or return to the sink; no other script's money may be spent in the same transaction; and what returns to the sink may not carry a datum hash. Each refusal has its own label: `sink-no-reference`, `sink-token`, `sink-envelope`, `sink-binding`, `sink-payload`, `sink-conservation`, `sink-foreign-script` and `sink-datum-hash`.

**If the name ends, the sink is dead.** A key can be ended for good by its controller. Then no output holds its token, nothing can be pointed at, and the money in the sink cannot move: there is no refund and no fallback. The registry's client refuses to book the same name again, and this scenario does not go past the client, so it makes no claim about what the chain would do.

**A compromised address can still be paid.** The sink pays the address registered at the moment of the move. If the address Alice registered is no longer safe, money moved before she updates it goes there. Only the controller of the key can change it.

**Anyone can register a name.** The registry belongs to no one: Carol made it, and she has no more say in it than Alice or Dave. Its rules protect the controller of each key, not the names: whoever's booking is folded first is the controller of `alice`. Paying by name is only as good as the knowledge that the name belongs to the person you mean, which Bob got by asking.

**What the programs check, and what they do not.** Singular's programs compare a registry with the release they belong to. An `open-datum` command (`insert`, `update`, `terminate`, `fold`, `inspect`) derives the registry's pinned policies from its release before it reads or writes anything, and stops with exit status 10 if one differs: a registry that pins another application, one that certifies keys differently, is refused with `registry-pin-mismatch application`. `singular registry describe` knows no application: it prints the one the registry pins and marks it `not-checked-against-any-blueprint`. Bob runs nothing but `describe` before he pays, which is why he also ran `check-registry`, which compares the application. No program of Singular checks Carol's page: `check-registry` applies the sink validator to the registry's active policy and compares the result with the sink script she published.

**Any number of registries can do this same job**; choosing one is a question of convenience, such as where the names you need already are, not of authority.
